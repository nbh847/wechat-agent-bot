# 开发 Goals

## 推进规则

- 所有 Goal 严格串行，一次只允许一个 Goal 处于“进行中”。
- 每个 Goal 开始前，先在 `ROADMAP.md` 标记“进行中”，并列出本轮验证命令。
- 只有实现和验证全部通过后，才能向散帅提交该 Goal 的验收结果。
- 散帅明确回复验收通过后，才把该 Goal 标记为“已确认”，并开始下一个 Goal。
- 验收未通过时，只修复当前 Goal，不提前实现后续 Goal。
- 新发现如果不影响当前验收，记录到后续 Goal 或待办，不顺手扩展范围。
- Goal 涉及删除文件、修改凭据、系统常驻配置或其他红线时，执行对应操作前仍需单独取得散帅确认。

## 已完成基线：iLink 可行性验证

状态：已验证，作为开发输入

已经证明：

- 本机能够从微信 iLink 接收文本并回复到原会话。
- 登录凭证可以持久化，进程重启后能够免扫码恢复。
- 第三方 SDK 登录轮询缺陷已复现，官方协议行为已对照。

该验证脚本不是正式架构，不能直接当作常驻服务交付。

## Goal 1：正式化最小 iLink 文本通道

状态：已确认（2026-08-13）

目标：把一次性 Echo 脚本整理成可测试、可停止、可恢复的微信通道组件，但尚不连接任何 AI Agent。

范围：

- 建立 `src/` 和 `tests/` 的最小目录结构与模块边界。
- 实现扫码登录、二维码自动刷新和可展示的二维码输出。
- 实现凭证、同步游标和 `context_token` 的安全持久化。
- 有效凭证必须从项目内状态恢复并持续复用；不得主动或定期刷新，只有服务端明确返回 token 失效时才清除并重新扫码。
- 实现文本接收、文本回复、消息 ID 去重、长轮询超时续接、有限退避和优雅停止。
- 识别 token 失效，停止错误重试并给出重新扫码状态。
- 日志不得包含 token、`context_token` 或完整消息正文。
- 移除第一版运行链路不再使用的 `@wechatbot/wechatbot` 依赖；执行依赖移除前按删除约束单独征求散帅确认。

不做：

- 不启动 Agent。
- 不执行本机命令。
- 不支持媒体、群聊和多账号。
- 不配置系统开机启动。

验收标准：

- 单元测试覆盖扫码状态、正常长轮询超时、token 失效、去重和状态持久化。
- 真实微信完成“启动 → 收到文本 → Echo 回复 → 重启 → 再次收发”。
- 重复投递同一消息不会产生两次回复。
- 类型检查、测试和依赖审计通过。

## Goal 2：安全任务入口与确认协议

状态：已确认（2026-08-13）

目标：在任何微信消息能够驱动 Agent 前，先定义并实现身份、范围和高风险操作边界。

范围：

- 只允许扫码绑定的散帅微信用户下发任务，其他发送者默认拒绝。
- 定义微信指令格式：普通任务、状态查询、取消任务和确认／拒绝高风险操作。
- 建立任务 ID、状态和确认请求的数据模型。
- 默认工作区固定为 `/Users/mac/workspace`；具体项目路径必须显式解析并校验边界。
- 微信任务可只读访问其他项目；对 `wechat-agent-bot` 之外任何项目的创建、修改、移动、删除或其他状态变更，必须先生成绑定任务 ID、目标项目和具体动作的二次确认，散帅确认后才能执行。
- 删除、Git 高风险操作、`.env`／密钥、数据库、全局依赖、公开发布和 Cloudflare 操作必须进入人工确认状态，不得直接执行。
- 定义消息正文、任务记录和审计信息的最小保存范围。

不做：

- 不接真实 Agent 执行任务。
- 不做复杂自然语言权限推断；第一版使用明确规则和确认状态。
- 不允许微信消息扩大已有本机规则权限。

验收标准：

- 未授权发送者、越界路径、跨项目写入和高风险请求都有测试并被拒绝或进入确认态。
- 确认码只能用于对应任务、对应动作并且一次有效。
- 普通任务能够生成持久化任务记录，但不会执行任何 Agent。
- 微信能收到清晰的接收、拒绝、待确认和取消结果。

## Goal 3：单 Agent 执行闭环

状态：已确认（2026-08-13）

目标：把一个已批准的微信任务交给本机 Agent 执行，并将最终结果回复微信。

范围：

- 定义与具体 Agent 无关的 `AgentRunner` 边界。
- 定义 Agent-neutral 调用协议；任何执行端只要实现该协议即可接入，不以 Agent 品牌作为核心配置或项目流程前提。
- 第一版只运行一个符合协议的 Agent 实例，不实现多 Agent 选择或调度。
- 每个任务绑定工作目录、会话标识、开始时间、结束状态和 Agent 输出。
- 支持启动、正常完成、失败、超时和用户取消。
- Agent 必须先读取目标项目的通用入口文档、`AGENTS.md`（如存在）和 `ROADMAP.md`（如存在）；工具专用规则文件仅作为补充，不得绕过项目规则。
- Agent 可以在确认前只读分析目标项目；任何跨项目写入必须验证 Goal 2 生成的有效二次授权，不能由 Agent 自行扩大范围。
- 将最终结果压缩为适合微信阅读的文本；完整输出只在确有必要且安全时本地保存。

不做：

- 不同时运行多个 Agent。
- 不实现自动 Agent 选择、并行 Agent 或多 Agent 协作。
- 不支持并发执行多个任务。

验收标准：

- 微信发送一个低风险、可验证的本地任务后，Agent 在指定项目中执行并把结果回复微信。
- 跨项目只读任务无需二次确认；跨项目写入任务在确认前不得产生文件或状态变更，确认后只能修改授权范围内的目标项目。
- 错误工作目录、Agent 启动失败、任务超时和取消都有可复现测试。
- 同一时刻最多执行一个任务；重复消息不会重复启动 Agent。
- Agent 产生的文件改动能够追溯到任务 ID。

## Goal 4：会话连续性与任务生命周期

状态：已确认（2026-08-13）

目标：让手机端能够持续与当前 Agent 会话交互，并看见长任务的真实状态。

范围：

- 支持口语化任务解析：用户可直接用自然语言描述目标项目、任务和期望输出，系统在内部转换为结构化任务；`task`、`status`、`cancel` 等显式命令继续作为精确控制和兜底入口。
- 自然语言涉及写入、高风险操作或目标／动作不明确时，必须先回显系统理解的项目、读写模式和具体动作，按 Goal 2 规则确认或补充信息后才能执行；不得用猜测扩大权限。
- 建立“微信会话 → 当前任务 ID → 执行适配器 ID → Agent 会话 ID → 默认目标项目”的持久化绑定；控制上下文属于 `wechat-agent-bot`，普通只读任务从该目录运行，已二次确认的写任务临时从授权目标项目运行且不复用普通会话；同一微信会话第一版只允许一个当前任务，历史任务不会被自动语义选中。
- 连续消息按固定优先级路由：显式指定任务／新会话／切换项目优先；未显式指定时默认续接当前任务；语义解析只辅助判断“当前任务追问还是新的独立目标”，不得凭语义在多个历史任务间猜测 `taskId`。
- 无法确定是续接还是新任务时，必须回显当前任务并询问用户选择，不得自行切换；用户可显式使用“继续 T0003”“新任务”“取消当前任务”等控制语句。
- 明确定义“当前 Agent”：当前任务、当前会话和当前工作目录三者的绑定关系。
- 支持同一会话的后续追问，不把每条消息都当成全新 Agent。
- 控制上下文大小：默认复用当前会话；上海时区跨自然日后的第一条任务或累计 30 次 Agent 调用后的下一条任务自动开启新会话；显式“新任务／新会话”立即开启新会话。自动轮换只携带不超过 1000 字的最小交接摘要，目标项目变化不触发轮换。
- 支持排队一个待执行任务，明确回复忙碌状态；第一版仍只串行执行。
- 支持“状态”“取消”“新会话”和“切换项目”等显式控制命令。
- 长任务返回有限频率的阶段进度，避免刷屏；结果必须区分成功、失败、取消和等待确认。
- 服务重启后恢复任务记录；不能安全恢复的运行中任务标记为中断，不自动重复执行。

不做：

- 不做多用户会话。
- 不做多个 Agent 会话并发运行。
- 不承诺恢复 Agent 进程内部无法持久化的瞬时状态。

验收标准：

- 日常口语化只读请求能够正确转换为结构化任务并执行；歧义、写入和高风险请求不会因自然语言解析而绕过确认规则。
- 连续追问默认进入当前任务和同一 Agent 会话；显式切换能准确改变绑定；歧义消息会询问而不会路由到错误历史任务。
- 连续两轮追问进入同一 Agent 会话，并保持相同项目上下文。
- 服务繁忙、取消、新会话和重启中断均有端到端验证。
- 进度消息不会泄露密钥、token、完整内部日志或思维过程。

## Goal 5：本地常驻运行与故障恢复

状态：已确认（2026-08-13）

目标：让服务在本机长期运行，并在普通网络和进程故障下恢复，不依赖手工守着终端。

范围：

- 实现服务启动、停止、状态检查和健康信息。
- 处理网络断开、DNS 失败、iLink 长轮询失败和有限退避重连。
- 实现单实例保护，防止两个进程消费同一账号游标。
- 日志轮转或有限保留，敏感字段脱敏。
- 设计 macOS `launchd` 运行方式和凭证路径。
- 在取得散帅对系统常驻配置的单独确认后，才实际安装并启用 `launchd` 配置。

不做：

- 不部署到公网或云服务器。
- 不引入容器、数据库、Redis、消息队列或监控平台。
- 不在未经确认时修改系统配置。

验收标准：

- 手动启动模式连续运行验证通过。
- 杀死进程、短时断网和恢复网络后，任务不会重复执行。
- 单实例保护有效，日志中无凭证和完整敏感消息。
- 经散帅批准安装后，重启服务或重启电脑能够恢复监听；若未批准，则只交付并验证安装方案，不声称已启用。

## Goal 6：MVP 端到端安全验收

状态：已确认（2026-08-13）

目标：证明“散帅通过手机微信随时调用当前本地 Agent”这一主路径可用，并验证主要失败和红线场景。

范围：

- 编写 MVP 使用说明、启动／停止说明、重新扫码流程和故障排查。
- 固化端到端验收用例及实际结果。
- 验证普通任务、连续追问、状态查询、取消、服务重启和网络恢复。
- 验证未授权发送者、路径越界、跨项目写入二次确认、重复消息和高风险操作确认。
- 核对所有运行依赖、许可证、敏感数据位置和日志策略。

不做：

- 不增加媒体、多账号、群聊、Web 管理后台或公开部署。
- 不把待确认能力写成已完成。

验收标准：

- 手机微信能够创建任务、查看进度、继续追问、取消任务并收到最终结果。
- 所有红线操作在执行前都需要散帅明确确认。
- 服务重启和网络恢复不会导致已处理任务重复执行。
- README、ROADMAP、运行说明、测试和真实验收记录一致。
- 散帅完成最终人工验收后，MVP 才能标记为完成。

## MVP 之后再评估

以下内容不属于当前 6 个 Goal：媒体消息、多微信账号、群聊、多 Agent 自动选择、并发任务、Web 管理后台、云部署和主动定时推送。只有出现明确真实需求后再建立新 Goal。
